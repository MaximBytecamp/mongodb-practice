# КТ-01 · Инвентаризация склада

Контрольная точка после модуля 1. Самостоятельная работа: разбора нет,
решения в репозитории нет и не будет — его разбирают на приёмке.

## Ситуация

На складе провели пересчёт. Учётные остатки лежат в базе, результат пересчёта
пришёл файлом. Нужно сверить одно с другим, привести учёт в порядок и написать
отчёт, по которому решение примет заведующий складом — человек, который
в базу не полезет.

| Источник | Что это | Поля |
|---|---|---|
| `sandbox.warehouse` | учёт: сколько числится | `sku`, `title`, `category`, `qty_accounted`, `shelf` |
| `kt01/stocktake.json` | пересчёт: сколько нашли на полках | `sku`, `counted`, `counted_by` |

Подготовка:

```bash
bash ../stend/load.sh
docker exec course-mongo mongosh sandbox --quiet --eval 'db.warehouse.countDocuments()'   # 21
```

Эталонные базы `shop`, `hh`, `logs`, `org` в работе не участвуют и меняться
не должны — это проверяется.

## Что сделать

1. **Загрузить пересчёт** из `stocktake.json` в коллекцию `sandbox.stocktake`
   одним запросом. Повторный запуск скрипта не должен двоить данные.
2. **Сверить учёт с фактом** по артикулу: разделить позиции на три группы —
   сошлось, недостача, излишек. Для каждой: сколько позиций и какие артикулы.
3. **Привести учёт в соответствие**: для позиций с расхождением записать
   фактическое количество в `qty_accounted` и добавить `last_stocktake` с датой.
   Позиции, где всё сошлось, не трогать — и доказать это числом `modified_count`.
4. **Пометить пустые полки**: позициям с нулевым фактическим остатком проставить
   `available: false`. У позиций, где товар есть, этого поля быть не должно.
5. **Записать в журнал** `sandbox.stocktake_log` один документ на инвентаризацию:
   дата, число позиций, число расхождений, суммарная недостача в штуках.
   Повторный запуск в тот же день не создаёт вторую запись.
6. **Написать отчёт** `inventory.md` по бланку [`report_template.md`](report_template.md).

## Требования

* каждое число в отчёте получено запросом, а не посчитано глазами; рядом
  с числом — сам запрос;
* изменения идут только в `sandbox`;
* перед массовым обновлением — `count_documents` с тем же фильтром;
* скрипт можно запустить дважды, и база придёт к тому же состоянию.

## Подсказки, которых хватит

* Пересчёт удобно грузить со своим `_id` — тогда повторная загрузка упрётся
  в `E11000`, а не создаст копии.
* Сверка делается в Python: читаем учёт проекцией, читаем файл, сравниваем
  по артикулу. Операторов для этого не нужно.
* Журнал за один день — классический случай для `upsert`: ключ документа
  собирается из даты.

## Самопроверка

```bash
python3 check.py
```

Проверяются результаты, а не способ. Правильные ответы скрипт не печатает —
только сообщает, сошлось или нет.

## Что сдаём

1. `inventory.py` — ваш скрипт.
2. `inventory.md` — отчёт по бланку с числами вашего прогона.
3. Вывод `python3 check.py`.
